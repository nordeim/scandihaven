# db:setup Script Plan: Fresh Postgres Container → Ready DB

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Add `pnpm db:setup` to `package.json` (root) as the single canonical command to initialize the database from scratch after `docker compose up -d` on a fresh (empty) postgres container — idempotent, no file generation, composes existing `db:migrate` + `db:seed`.

**Architecture:** Shell-chain script in root `package.json` delegating to the existing `@scandihaven/db` workspace scripts (no new TS file, no new package, no Turbo task). `db:setup = db:migrate && db:seed`. `db:generate` is explicitly *not* part of setup (it writes migration files, requires review — see §4).

**Tech Stack:** pnpm workspaces, `package.json` scripts, `dotenv` (already in @scandihaven/db), `drizzle-kit generate/migrate`, `tsx` seed, postgres:17-alpine healthcheck

## 0. ANALYZE — Current State

**Root `package.json` scripts (verified):**
```json
"db:migrate": "pnpm --filter @scandihaven/db migrate",
"db:seed":    "pnpm --filter @scandihaven/db seed",
"db:reset":   "pnpm --filter @scandihaven/db reset",
"db:generate":"pnpm --filter @scandihaven/db generate"
```
No `db:setup`. Quick Start uses `pnpm db:migrate && pnpm db:seed` inline; AGENTS.md repeats that; README Troubleshooting still references `pnpm db:seed` alone for volume rename.

**Package `@scandihaven/db` scripts:**
- `migrate`: `tsx src/scripts/migrate.ts` → `drizzle-orm migrate` (forward-only, reads `drizzle/` folder, currently `0000_large_sphinx.sql` + meta)
- `seed`: `tsx src/scripts/seed.ts` → `ensureSeeded()` (advisory-lock + natural-key upserts, idempotent, refuses non-local hosts)
- `reset`: `tsx src/scripts/reset.ts` → `DROP SCHEMA public CASCADE; CREATE SCHEMA` (local-only guard, does NOT run migrate/seed — caller must)
- `generate`: `drizzle-kit generate` (writes new SQL under `drizzle/`, dev-time only, requires `drizzle.config.ts` + DATABASE_URL. `drizzle.config.ts` currently defaults to `scandihaven:scandihaven@.../scandihaven` (stale — should be updated separately but not this plan's scope)

**Fresh container state (after `docker compose down -v && up -d`):**
- Volume `postgres_data` empty → `initdb` → `00-create-extensions.sql` installs `pgcrypto`+`pg_trgm` (verified via `\dx`)
- No tables, no `drizzle.__drizzle_migrations`, no seed data
- Health: `start_period: 10s`, then `healthy` → ready for TCP 5432
- `DATABASE_URL=postgresql://scandihaven_user:scandihaven_secret@localhost:5432/scandihaven_dev` (from `.env.example`, matches compose)

**What fresh setup needs:**
1. Migrations applied (`citext` extension via `0000_large_sphinx.sql`, all 40 tables)
2. Seed data (categories, products, variants, inventory, etc., idempotent)
3. No `generate` — that would inspect `packages/db/src/schema/*.ts` and write a new migration file if schema drifted; running it automatically on every fresh setup would commit unchecked migrations and is slow (requires DB connection + file I/O). Fresh container has no schema drift; `migrate` already covers it.

**What `db:setup` should NOT do:**
- `db:generate` — dev-time file generation, not runtime init. Including it would violate YAGNI and create unreviewed SQL.
- `db:reset` — destructive `DROP SCHEMA`; fresh container already empty; `reset` is the other direction (existing DB → empty → migrate). Setup must be safe on both empty and already-seeded DBs (idempotent).
- Health-wait loop — tempting, but `docker compose ps --status running` + `pg_isready` already exists as compose healthcheck; adding a shell wait loop adds complexity. If needed, document `until docker inspect --format='{{.State.Health.Status}}' == healthy` as optional pre-step, but don't bake into `db:setup` (keeps script pure).

## 3. RISKS & MITIGATIONS

| Risk | Impact | Mitigation |
|---|---|---|
| Running `generate` in setup checks in unreviewed migrations | High — writes files, may break CI | Exclude `generate` from setup (D3); manual `pnpm db:generate` remains separate |
| `setup` runs before DB healthy → ECONNREFUSED | Medium | Document `sleep 12` or `until pg_isready` pre-step; healthcheck already 10s; shell-chain `&&` fails fast with clear error |
| `setup` on non-empty DB drops data if `reset` included | High | Exclude `reset` from setup (D4); `reset` is explicit destructive command |
| DATABASE_URL not set when running via `pnpm --filter` | Medium | Keep `.env` at root + `packages/db/.env` (gitignored) or export; note in docs |
| Old docs still show `migrate && seed` inline, new `setup` duplicates | Low — confusion | Keep both: `db:setup` as canonical, inline as comment/alternative |
